VALID ROLES (stored in users.role):

ABAC RULES (enforce in middleware, not just role checks):
  - Teachers may only access records for students currently in their assigned class.
  - Substitute teachers have the same constraint as teachers but only for the
    active substitution period (check against a substitution_schedule table).
  - Counselors may access records for students assigned to their caseload,

  - School Heads may read all records within their tenant but cannot modify

  - Board Members receive anonymized / aggregated data only — no PII.
  - Case Reviewers have read-only access to cases assigned for review.
  - IT Admins have full access to system configuration but are blocked from
    reading case descriptions and incident narratives (data minimization).
  - Pattern Detection alerts are visible ONLY to Counselors and School Heads.

Generate an Express.js middleware factory:
  checkPermission(resource: string, action: 'create'|'read'|'update'|'delete')
  that enforces both RBAC and ABAC rules from a single call point.

SECTION 6 — CORE BUSINESS LOGIC
================================================================================

Generate the following service-layer modules in TypeScript:

6.1 RISK LEVEL AUTO-CALCULATION (cases.service.ts)
  When a new incident is linked to a case, recalculate risk_level:
    - Count incidents in last 30 days for this student
    - If any incident is CRITICAL severity → case risk = CRITICAL
    - If 3+ HIGH incidents in 30 days → case risk = HIGH
    - If 5+ MEDIUM incidents in 30 days → case risk = HIGH
    - Otherwise maintain current risk or default LOW
  Always set risk_level_source = 'AUTO'. Allow manual override to set
  risk_level_source = 'MANUAL', which locks auto-recalculation until
  a counselor explicitly unlocks it.

6.2 PATTERN DETECTION ENGINE (pattern-detection.service.ts)
  Implement the following rules (each rule generates an alert if triggered):

  Rule: RAPID_ESCALATION
    Condition: Student has 3+ incidents of increasing severity within 14 days
    Alert severity: HIGH
    Expires: 7 days after creation

  Rule: REPEATED_SAME_CATEGORY
    Condition: Student has 4+ incidents of the same category within 30 days
    Alert severity: MEDIUM
    Expires: 5 days after creation

  Rule: ABSENCE_OF_INTERVENTION
    Condition: An OPEN case with HIGH or CRITICAL risk has no intervention
               recorded in the past 10 days
    Alert severity: HIGH
    Expires: 3 days after creation

  Rule: CRITICAL_INCIDENT_NO_FOLLOWUP
    Condition: A CRITICAL-severity incident was recorded more than 24 hours
               ago and has no linked intervention
    Alert severity: CRITICAL
    Expires: 48 hours after creation

  All alerts must:
    - Never auto-act. Alerts are advisory only. A human must review each one.
    - Store a snapshot of the triggering data in pattern_data JSONB column.
    - Not be created if an unreviewed alert for the same rule + student exists.
    - Be visible only to COUNSELOR and SCHOOL_HEAD roles.

6.3 DATA LIFECYCLE ENGINE (data-lifecycle.service.ts)
  Implement a scheduled job (run daily via node-cron):

  Stage 1 — ACTIVE: Default state. No action.
  Stage 2 — SUMMARIZE: After 2 years from case closed_date,
    compress incident descriptions to a summary. Preserve category,
    severity, and dates. Store summary in cases.summary. Null out
    incident descriptions to minimize PII.
  Stage 3 — ARCHIVE: After 5 years from case closed_date,
    move case metadata to a cold_archive table and soft-delete from
    the main cases table.
  Stage 4 — DELETE: After 7 years (or on right-to-be-forgotten request),
    hard-delete archived records. Log deletion in audit_logs with reason.

  Relevance Decay: When returning historical incidents to the frontend,
  attach a relevance_weight field calculated as:
    weight = 1.0 / (1 + months_since_incident / 12)
  This is informational only — do not filter records based on it.

6.4 CONSENT PROPAGATION (consent.service.ts)
  When a consent is revoked:
    - Set revoked_at on the consent record
    - Identify all media_assets linked to the student
    - Set media_assets.retention_expiry = now() + 30 days (grace period)
    - Log each affected asset in audit_logs with action = CONSENT_REVOKED_PROPAGATION
    - If consent_type covers case data, flag cases for counselor review
      rather than auto-deleting (human review required before deletion)

6.5 NEUTRAL LANGUAGE ENFORCEMENT (language-check.service.ts)
  Before saving any incident description or intervention note, run a check
  against a configurable blocklist of labeling or stigmatizing terms.
  If a flagged term is found:
    - Set incidents.language_flag = true
    - Return a 400 response with the specific terms flagged and suggested
      neutral alternatives
    - Do NOT save the record until the author revises the text
  Provide a default blocklist in a JSON config file, extensible per tenant.

SECTION 8 — SECURITY REQUIREMENTS
================================================================================

Implement the following security controls in code:

8.1 ENCRYPTION
  - Encrypt students.national_id at the application layer using AES-256-GCM
    before writing to the database. Store the IV alongside the ciphertext.
  - All API responses must redact this field unless the caller has
    IT_ADMIN or SCHOOL_HEAD role.
  - TLS enforced in production (document how to configure via reverse proxy).

8.2 AUTHENTICATION
  - JWT access tokens: 15-minute expiry
  - Refresh tokens: 7-day expiry, stored in Redis, rotated on each use
  - Revoke all refresh tokens on password change or account deactivation
  - Rate-limit login endpoint: max 5 failed attempts per 15 minutes per IP

8.3 AUDIT LOGGING
  Create a utility function: auditLog(action, entityType, entityId, before, after)
  Call it inside every service method that mutates data.
  The audit_logs table must never be writable by application code except through
  this utility function. Enforce with a separate DB role that has INSERT-only
  privileges on audit_logs.

8.4 MULTI-TENANCY ISOLATION
  - On every authenticated request, extract tenant_id from the JWT payload
  - Set PostgreSQL session variable: SET LOCAL app.tenant_id = '<tenant_id>'
  - All RLS policies use this variable, providing database-layer isolation
    even if application code has a query bug

8.5 RIGHT TO BE FORGOTTEN (RTBF)
  Implement POST /api/admin/rtbf-request with the following steps:
    1. Verify caller is IT_ADMIN
    2. Validate consent exists for the deletion request
    3. Soft-delete all cases, incidents, interventions, observations for student
    4. Set retention_expiry = now() on all media_assets for student
    5. Null out students.national_id, full_name → replace with "DELETED_[hash]"
    6. Log entire operation in audit_logs with action = RTBF_EXECUTED
    7. Return a signed, timestamped confirmation PDF (for legal evidence)

SECTION 10 — CODE QUALITY STANDARDS
================================================================================

All generated code must follow these rules without exception:

  - TypeScript strict mode: true in tsconfig.json
  - No use of `any` type. Use `unknown` and narrow where needed.
  - All async functions must handle errors. No unhandled promise rejections.
  - Zod for all input validation. Never trust raw req.body.
  - Environment variables accessed only through a validated config module
    (use zod to parse process.env at startup and fail fast if required vars missing).
  - Database queries use parameterized statements only. No string interpolation in SQL.
  - All mutations wrapped in database transactions where more than one table is affected.
  - Folder structure:
      /src
        /api          (Express routes)
        /services     (business logic)
        /db           (query modules, migrations)
        /middleware   (auth, permissions, tenant)
        /types        (shared TypeScript types/interfaces)
        /utils        (auditLog, encryption, language-check helpers)
        /jobs         (cron jobs — data lifecycle, alert detection)
      /frontend
        /app          (Next.js App Router pages)
        /components   (reusable UI components)
        /lib          (API client, auth helpers)

  - All sensitive operations (RTBF, bulk delete, consent revocation) must log
    BEFORE executing and log AFTER executing, so partial failures are traceable.
